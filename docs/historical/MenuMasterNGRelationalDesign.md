## 1. FINAL PROPOSED DATABASE SCHEMA

Every table uses a UUID primary key called id, generated by the database. Every business owned table carries business_id so data is isolated per business. Timestamps are created_at and updated_at where useful.

**businesses**
* id (PK)
* owner_id (FK to auth.users)
* name, business_type, currency (default ₦), phone, logo, location
* created_at, updated_at
* Relationships: one owner (a user) owns a business. A business has many of everything below.

**business_users** (who can access a business, and as what)
* id (PK)
* business_id (FK businesses), user_id (FK auth.users)
* role (owner, manager, staff)
* status (active, invited, disabled)
* created_at
* Relationships: links users to businesses. This is what makes real staff accounts and the two doors possible.

**subscriptions** (billing, moved off the old row)
* id (PK)
* business_id (FK businesses)
* plan (trial, founding, monthly, yearly)
* status (trialing, active, past_due, cancelled)
* trial_start, current_period_end
* paystack_reference
* Relationships: one business has one active subscription. This preserves your trial and paid state safely.

**suppliers** (optional, referenced by ingredients)
* id (PK), business_id (FK), name, phone, notes

**ingredients**
* id (PK), business_id (FK)
* name, category, base_unit (for example kg, litre, piece)
* current_unit_cost (the latest cost per base unit)
* supplier_id (FK suppliers, optional)
* is_active (soft delete, so nothing is ever truly lost)
* created_at, updated_at
* Rules: unique name per business (no duplicates). current_unit_cost is always the latest row from price history.

**ingredient_price_history** (append only, never overwritten)
* id (PK), ingredient_id (FK ingredients)
* purchase_quantity, purchase_unit, purchase_price
* calculated_unit_cost (purchase_price converted to cost per base unit)
* effective_date, created_at
* Rules: every price change inserts a new row. Old prices are never deleted.

**measurement_units** (supports the picture based guide)
* id (PK), business_id (FK, or null for global defaults)
* name (for example Derica, Mudu, Cup), picture_key
* base_unit, conversion_to_base (for example 1 Derica of rice equals a set number of kg)
* Rules: lets non readers pick a unit by picture while costing stays accurate.

**recipes** (production and cost side)
* id (PK), business_id (FK)
* name, category
* yield_quantity, yield_unit (how many portions or how much a batch makes)
* packaging_cost, labour_cost, gas_cost, transport_cost, other_overhead (the separate cost lines)
* notes, created_at, updated_at
* Relationships: has many recipe_ingredients. Feeds a menu_item.

**recipe_ingredients** (the join, kept from today because it is already good)
* id (PK), recipe_id (FK recipes), ingredient_id (FK ingredients)
* quantity, unit, calculated_cost (quantity times the ingredient unit cost, recomputed on change)
* Rules: deleting a recipe cascades to its recipe_ingredients. An ingredient in use cannot be hard deleted, only deactivated.

**menu_categories**
* id (PK), business_id (FK)
* name, sort_order, is_active
* Rules: your categories (Rice dishes, Swallow, Beans, and so on) live here, reorderable and hideable.

**menu_items** (sellable and priced side)
* id (PK), business_id (FK), recipe_id (FK recipes), category_id (FK menu_categories)
* name, selling_price
* pricing_method (margin, markup, fixed), target_margin, target_markup
* recommended_price, min_price (computed and stored for speed)
* status (profitable, low_margin, loss)
* created_at, updated_at
* Rules: this is what a customer buys. Cost comes from its recipe. Price and profit live here. Margin and markup are stored as separate fields and never mixed.

**customers**
* id (PK), business_id (FK), name, phone, email, notes, created_at

**orders** (also covers quick sales and catering, via order_type)
* id (PK), business_id (FK), customer_id (FK customers, optional)
* order_type (order, quick_sale, catering)
* order_date, status, payment_status, delivery_status
* discount, delivery_fee
* total_revenue, total_cost, total_profit, profit_margin
* created_at
* Rules: profit is calculated from its items, not typed by hand.

**order_items**
* id (PK), order_id (FK orders), menu_item_id (FK menu_items)
* quantity, selling_price, cost, profit
* Rules: cost is captured at the time of sale, so later price changes do not rewrite history.

Recommended additions beyond your minimum, because they are technically needed:
* subscriptions (billing, above), suppliers, measurement_units, and the separate cost line fields on recipes. I folded sales into orders with an order_type to avoid two near identical systems. If you prefer a separate sales table, we can split it, but one clean orders table is simpler and safer.

## 2. LEGACY DATA MAPPING

Each current app_state row (one per vendor) becomes one business, owned by that vendor's user. Then the bundle inside maps like this.

| From app_state.data | To new tables |
|---|---|
| settings (bizName, currency, phone) | businesses |
| settings (trial_start, subscribed on the row) | subscriptions |
| settings (margin, overhead) | business default costing settings (on businesses) |
| ingredients[] (name, category, unit, cpu, updated) | ingredients (name, category, base_unit, current_unit_cost) plus one seed row in ingredient_price_history (calculated_unit_cost equals cpu, effective_date equals updated) |
| recipes[] (name, category, overhead, margin) | recipes (name, category, other_overhead equals overhead, yield defaults to 1 portion) plus menu_items (recipe_id, name, target_margin equals margin, selling_price equals the current computed price, status computed) |
| ri[] (rid, iid, qty) | recipe_ingredients (recipe_id and ingredient_id mapped to new ids, quantity equals qty, unit from the ingredient, calculated_cost equals cpu times qty) |
| customers[] | customers |
| orders[] (items, customer, date) | orders plus order_items, with cost and profit computed from recipe costs at migration time |
| id counters (nig, nrec, and so on) | discarded, replaced by UUIDs, with an old id to new id map kept during migration |

The key move: today recipe and price are one thing. In the new model, cost lives on recipe and price lives on menu_item. Migration creates both from each current recipe.

## 3. MIGRATION STRATEGY

1. **Back up.** Export the entire app_state table from Supabase (full copy) and store it safely. Also record the current Vercel deployment as the rollback point, and keep the current index.html.
2. **Create the new tables.** Add all tables above in Supabase, alongside app_state. The current app is untouched and keeps working.
3. **Migrate data.** Run a one time migration that reads each app_state bundle and writes into the new tables, building an old id to new id map per vendor, seeding price history, and computing order costs. It is idempotent, so it can be safely re run and never double inserts.
4. **Verify counts.** For every vendor, check that the number of ingredients, recipes, recipe ingredients, customers, and orders in the new tables exactly matches the bundle. Log any mismatch. Zero mismatches required.
5. **Verify costing.** Recompute cost, price, and margin from the new tables for a sample of recipes and compare to the old engine. They must match to the naira. See section 7.
6. **Switch the app.** Deploy the new version that reads and writes the tables. This is the large piece, because every screen changes from loading one bundle to querying tables. The old bundle stays frozen and untouched.
7. **Keep rollback ready.** If anything is wrong, redeploy the previous version in one click. Because app_state was never modified, no data is lost. Keep app_state preserved read only for a safety window (for example 60 days) before retiring it.

We migrate a copy and validate before cutover. We do not modify the old bundle, so it is always a clean fallback.

## 4. DATA INTEGRITY

* **Duplicate ingredients:** a uniqueness rule on business plus ingredient name. New entries that clash are caught, not silently duplicated.
* **Orphaned recipes and menu items:** foreign keys enforce that a recipe ingredient must point to a real recipe and a real ingredient, and a menu item to a real recipe and category. Deleting a recipe cleanly removes its recipe ingredients. Menu items cannot point to a missing recipe.
* **Ingredient deletion:** an ingredient used by any recipe cannot be hard deleted. It is deactivated (is_active false) instead, so recipes and history stay intact.
* **Cross business leakage:** every table carries business_id and is protected by row level security (section 5). The database itself refuses to return another business's rows, even if the app has a bug.
* **Incorrect ingredient costs:** the unit cost is always computed from purchase price and quantity with unit conversion, stored in price history, and recipe costs recompute whenever an ingredient cost changes. Values must be non negative and units compatible.
* **Historical price loss:** price history is append only. A price change never overwrites the old value, it adds a new dated row. The current cost is simply the latest row.

## 5. SUPABASE SECURITY (ROW LEVEL SECURITY)

Row level security is turned on for every table. The core rule, in plain words: you can only see or change a row if it belongs to a business you are a member of.

* A helper decides, for the logged in user, which businesses they belong to (from business_users where the user is active).
* Every business owned table allows a row only if its business_id is in that set. Example policy logic: allow the row when business_id is in the set of businesses the current user actively belongs to.
* Child tables without a business_id of their own (recipe_ingredients, order_items) are checked through their parent (the recipe or the order must belong to an allowed business).
* Role inside a business controls sensitivity. Staff (customer care) get access only to a safe view that shows what they need, order taking, customers, and menu names and prices, but never cost, profit, recipes, or ingredients. Owners and managers get full access. This is the proper, database enforced version of your two doors.
* Billing (subscriptions) is readable by business members but only written by the secure server side process (the Paystack webhook), never by the app directly.

The guarantee: one business can never reach another business's ingredients, recipes, menu, orders, customers, reports, or staff, because the database blocks it, not just the app.

## 6. EXISTING APP PRESERVATION

* The current app keeps running unchanged while we design and while the new tables are created, because those steps are additive and never touch app_state.
* We build the new table based version separately and validate it against the old engine before any cutover.
* We do not remove the current costing engine or the app_state data until the new version is proven correct in real use and the safety window passes.
* The old margin formula stays as the reference that the new system must match exactly.
* Users see no downtime. Cutover is a single deploy. If it fails, we roll back instantly to the version that reads the old bundle, with all data intact.

## 7. MIGRATION TEST: OLD EQUALS NEW

Before cutover, we prove the new system produces the same numbers as the old one. For a representative set of recipes, including the seeded Jollof Rice, we compute with both and require an exact match on:

* Ingredient cost (unit cost times quantity)
* Recipe cost (ingredients plus overhead and cost lines)
* Batch cost (with yield equal to 1, this equals the old recipe cost)
* Portion cost (batch cost divided by yield, equals the old cost when yield is 1)
* Selling price (cost divided by one minus margin, the same formula)
* Profit (selling minus cost)
* Margin (the set percentage)

Pass rule: every value matches to the naira. Any difference stops the cutover until explained.

**Price change test:** change one ingredient's cost by adding a new price history row, then confirm that every recipe using that ingredient recalculates its cost, that the menu item's recommended price updates, that the new numbers match a hand calculation, and crucially that the old price is still present in history. This proves both the recalculation and that no history is lost.

**Count test:** for each vendor, the number of ingredients, recipes, recipe ingredients, customers, and orders in the new tables equals the bundle exactly.

**Rollback test:** practice restoring the previous deployment and confirm the old bundle is untouched, so we know the safety net works before we ever need it.

Only when all four tests pass do we cut over.
