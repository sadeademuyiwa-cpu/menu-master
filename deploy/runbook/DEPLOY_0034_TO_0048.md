### Revision 2 — 2026-08-31, after the first PRE_DEPLOY_AUDIT run

The first audit run failed closed on check 1 with fingerprint
`4285b6818c1d210150996bc7e13420ad` against an expected
`26a45d7d98026721366ec58a66cb6d1b`, all 23 other checks passing.

That was a **fault in the fingerprint, not drift in production**. The original
fingerprint sorted its signatures using the database's own collation. The
rehearsal replica is `C.UTF-8`; a Supabase project is created `en_US.UTF-8`.
Re-sorting this replica's *own, unchanged* 0033 catalogue under an ICU/`en_US`
ordering reproduces production's `4285b6818c1d210150996bc7e13420ad` **exactly** —
which a different set of functions could not do. Evidence:
`evidence/FINGERPRINT_ROOT_CAUSE.txt`; reproduce it yourself with
`DIAGNOSE_FINGERPRINT.sql` (read only).

The fingerprint is now built from bare type names ordered `COLLATE "C"`, so it
depends on neither the collation nor `search_path`. Expected values changed to
**`0566a47b992936813893b40bcba5c6ac`** (0033) and
**`e24f3871788893cafd1fc17c70fe41d5`** (0048). The gate was **not** weakened —
it still fails closed at 0034, at 0042 and at 0048.

### Revision 3 — 2026-08-31, after the second production attempt

The second attempt aborted on `ERROR: 42883: function "local_pre_request()"
does not exist`, raised by a self-check inside migration 0048.

`local_pre_request()` is created only by `tests/0000_local_supabase_shim.sql`,
which labels it *"LOCAL ONLY … Never run against Supabase: the platform provides
this itself."* Every rehearsal database is built by applying that shim first, so
the function was always present locally and the check always passed. The replica
was faithful to the migration set and **not** to the environment.

`has_function_privilege()` on a *text* signature raises 42883 for a function
that does not exist — it does not return false — so the assertion aborted the
whole transaction on the one database it existed to protect. The `and exists
(… rolname = 'authenticator')` guard could not help: `authenticator` does exist
on Supabase, and the throwing operand is evaluated first regardless.

The check was replaced, not removed, with three things that name no
environment's function:

* an ACL snapshot of every function in `public` taken before the revoke loop,
  asserted afterwards to show that **only** `fn_*` functions changed — this is
  the property the hardcoded check was reaching for, and it covers the hook
  whatever it is called;
* an assertion on whatever pre-request hook the database actually configures,
  read from `pgrst.db_pre_request` and resolved with `to_regprocedure`, which
  returns NULL instead of raising;
* `aclexplode()` in place of the `'=X/postgres'` / `'anon=X/postgres'` ACL text
  literals, which silently stopped matching whenever the owner was not
  `postgres`.

New tooling so this class of defect cannot ship again:

* `scripts/audit_env_assumptions.sh` — static audit; fails on a literal
  signature in a privilege lookup, on any reference to a shim-only name, on an
  owner-bearing ACL literal, and on `current_setting` without `missing_ok`.
  `scripts/build_phase6_deploy.sh` now refuses to generate a bundle unless it
  passes.
* `PRE_DEPLOY_AUDIT.sql` checks **25–28** — `auth.uid()`, the four platform
  roles, *this is not the harness database*, and the configured pre-request
  hook. 24 checks became 28.
* A production-faithful replica builder that removes the shim-only function
  before any migration runs. The whole battery now runs against it.

## STEP 4 — RUNTIME_PROBE.sql   (creates data, then throws it away)

**This is the step that would have caught the first failure.** Every other check
reads the catalogue. A PL/pgSQL body is **not** resolved against the catalogue
when the function is created — a function can reference a column that does not
exist, be created successfully, pass every schema check, and fail only when a
customer records a sale. On a database with Phase 6 but not its prerequisites,
STEP 3 reports 10/10 PASS and the first sale fails with
`column "seq" does not exist`.

### How it operates safely on a production database with no data

Production has no business, no recipe and no ingredient, so the probe cannot
borrow existing data — it **builds its own and discards it**:

- It runs inside `begin … rollback`. **Nothing it creates is ever committed.**
- **It never touches `auth.users`.** `accounts`, `businesses`, `ingredients`,
  `recipes`, `customers` and `order_lines` have no foreign key to `auth.users`,
  and `orders.created_by` / `finalised_by` are nullable — verified against the
  live schema. No login is created, altered or read.
- Every row it makes is named `__probe__…`, so it is unmistakable.
- It counts `auth.users` before and after and **fails if the number moves**.
- After the `rollback`, a final query — outside the transaction — asserts that
  **zero** `__probe__` rows survived.

It builds ₦85,000 of rice over 50 kg (₦1.70/g), a 4,500 g batch at a 500 g
portion, sells two at ₦2,000, and confirms.

**Expected: two tables.**

```
verdict | detail
PASS    | lines_frozen=1, cost frozen at 850.0000 (expect 850.0000),
          net revenue 4000.00 (expect 4000.00), auth.users 7 -> 7 (must be equal)

cleanup_verdict | detail
PASS            | 0 __probe__ row(s) survived the rollback (must be 0)
```

> **STOP if either row is not `PASS`, or on any error.** Go to ROLLBACK.
> `ERROR: column "seq" does not exist` here means the prerequisites did not land
> — which STEP 1 should have prevented.

## ROLLBACK — is the old strategy still sufficient?

**No, and it has been regenerated.**

At six migrations a rollback could be six files run one at a time. At **fifteen**
that is fifteen chances to stop halfway and leave production in a state nobody
has tested. Each source rollback also carried its own `begin`/`commit`, so a
failure partway through left some reversed and some not.

`ROLLBACK.sql` is now **one transaction** containing all fifteen reversals in
order 0048 → 0034, with the per-file transaction control stripped, and it ends by
asserting it is back at the 0033 fingerprint.

**When to run it:** only if STEP 2 **committed** and STEP 3 or STEP 4 then
failed. If STEP 2 itself failed, it already undid itself — run STEP 1 to confirm
and stop.

**Expected:**

```
NOTICE:  ROLLBACK OK: back at the 0033 catalogue, 116 policies, auth.users untouched.
COMMIT
```

Then re-run `PRE_DEPLOY_AUDIT.sql`; it must accept the database again — 24 rows,
all PASS.

**What it deliberately does not undo:** any sale confirmed after the deploy keeps
its frozen cost, and any `finalised_at` 0045 recorded stays. On this database
both are nothing at all — production holds zero orders — but the rule is stated
so it remains true when that changes. **`auth.users` is never touched, forward or
back.**

## Why a backup matters less here than it did

Production holds **0 accounts, 0 businesses, 0 recipes, 0 orders, 0 cost
snapshots**. There is no financial history to lose. The seven login accounts are
never read or written by any of the fifteen migrations, and STEP 1 row 16, STEP 3
rows 12–13 and the probe's own before/after count all assert that independently.

The Free-plan backup guidance in `PHASE6_STEP0_FREE_PLAN.md` still applies and is
still worth doing — but the thing it protects, trading data, does not yet exist.
